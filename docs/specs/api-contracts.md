# API contracts specification

Sources: [CHALLENGE.md](../../CHALLENGE.md) §§1, 3, 5, and 6; [ADR 0005](../adr/0005-idempotent-match-submission-outbox.md) and [ADR 0006](../adr/0006-msw-in-production.md).

The challenge mandates typed REST integration through Axios and TanStack Query, consistent ranking/history, and persistent idempotent recovery. Endpoint paths, shapes, ordering details, storage names, and policies below are **proposed** contracts. TypeScript blocks describe interfaces only; this document adds no executable code.

## Endpoints

| Method and path | Request | Successful response |
| --- | --- | --- |
| GET /api/ranking | Required configKey; page and pageSize query parameters | 200, Paginated<RankingEntry> for exactly that configuration |
| GET /api/players/:playerId/matches | playerId path parameter; page and pageSize query parameters | 200, Paginated<MatchRecord> for that player |
| PUT /api/matches/:matchId | matchId path parameter; JSON MatchRecord body | 201 for first creation; 200 for existing record; MatchRecord body in both cases |

All responses use JSON. URL-encode path identifiers and configKey. Every completed record contributes one history record and one ranking entry; other players come from fixtures. Abandoned matches have no record or submission.

## Request and response shapes (proposed)

Configuration names and numeric units correspond to [Gameplay configuration](gameplay.md#game-configuration). The configuration snapshot contains every balancing parameter, not only the two Options fields.

```typescript
interface GameplayConfig {
  sessionTime: number; // seconds
  enemySpawnInterval: number; // seconds
  chaserSpawnWeight: number;
  shooterSpawnWeight: number;
  minSpawnDistance: number; // logical units
  playerHp: number;
  chaserHp: number;
  shooterHp: number;
  playerMoveSpeed: number; // logical units/second
  chaserMoveSpeed: number;
  shooterMoveSpeed: number;
  playerRotationSpeed: number; // radians/second
  chaserRotationSpeed: number;
  shooterRotationSpeed: number;
  frontProjectileDamage: number;
  sideProjectileDamage: number;
  shooterProjectileDamage: number;
  frontProjectileSpeed: number; // logical units/second
  sideProjectileSpeed: number;
  shooterProjectileSpeed: number;
  frontProjectileRange: number; // logical units
  sideProjectileRange: number;
  shooterProjectileRange: number;
  frontProjectileLifetime: number; // seconds
  sideProjectileLifetime: number;
  shooterProjectileLifetime: number;
  frontFireCooldown: number; // seconds
  sideFireCooldown: number;
  shooterAttackRange: number; // logical units
  shooterFireCooldown: number; // seconds
  chaserCollisionDamage: number;
}

interface MatchRecord {
  matchId: string;
  playerId: string;
  playerName: string;
  playedAt: string; // UTC ISO 8601 timestamp at completion
  score: number; // non-negative integer
  durationMs: number; // integer active simulation milliseconds
  endReason: 'time-expired' | 'player-death';
  config: GameplayConfig;
  configKey: string;
}

interface RankingEntry {
  rank: number; // absolute 1-based position within configKey
  matchId: string;
  playerId: string;
  playerName: string;
  playedAt: string;
  score: number;
  durationMs: number;
  configKey: string;
}

interface PaginationRequest {
  page?: number;
  pageSize?: number;
}

interface RankingRequest extends PaginationRequest {
  configKey: string;
}

interface Paginated<T> {
  items: T[];
  page: number;
  pageSize: number;
  total: number;
  totalPages: number;
}

interface ApiError {
  code: 'validation-error' | 'not-found' | 'rate-limited'
    | 'internal-error' | 'unavailable' | 'timeout' | 'connection-failure';
  message: string;
  details?: Record<string, string>;
}
```

playedAt is generated by the shell at completion, outside the core. Proposed: durationMs is floor(active simulation seconds × 1000); it excludes paused time and never exceeds sessionTime × 1000. API failures do not change the frozen payload.

## Pagination (proposed)

page is 1-based and defaults to 1. pageSize defaults to 10 and accepts integers from 1 to 50. Invalid integers or bounds return 400; pages beyond the available range return 200 with empty items and unchanged totals. total counts all matching records before slicing; totalPages = ceil(total / pageSize), including 0 for an empty dataset.

History sorts by playedAt descending, then matchId ascending, using normalized timestamps and stable string comparisons. Ranking sorts before pagination; ranks do not restart on each page. Data can change between requests; this contract does not promise a frozen multi-page snapshot.

## Configuration groups and ranking (proposed)

Derive configKey as `v1:` followed by a compact JSON object containing every GameplayConfig field sorted by field name, with validated numeric values serialized consistently. Compare the key to the supplied configuration on first registration; reject mismatches. Encode the key when placed in a query string. A future incompatible configuration schema requires a new key version.

The same full configuration yields the same key. Seed, player identity, date, canvas size, and network scenario are excluded; balancing parameters are included. This definition assumes one arena/ruleset for v1; a later ruleset or map change must revise the grouping version.

Within one configKey, order by score descending, durationMs ascending, playedAt ascending, then matchId ascending. Normalize playedAt to UTC before comparison; use locale-independent lexical order for matchId. One entry represents one match, including multiple matches by the same player; do not collapse to a personal best. The comparison order is a proposed deterministic choice, not prescribed by §5.

## PUT idempotency (proposed)

At the first completion transition, generate matchId once in the shell and persist its immutable payload to the outbox before attempting HTTP. Match IDs are globally unique within the local mock database; proposed generation: browser cryptographic UUIDs. The body matchId must equal the path parameter.

For a new matchId, validate the full payload and insert one confirmed record. For an existing matchId, return the stored record with 200 without updating it or adding another entry, including when other body fields differ. Check identifier agreement before lookup; the first confirmed payload wins. Both ranking and history derive from this same confirmed-record collection.

Persist the mock commit before acknowledging it. A timeout can occur after commit; the client retains its outbox entry and reuses the same matchId on retry. Remove pending state only after receiving confirmation for that identifier. Repeated clicks share a per-match in-flight submission; boot replay and manual retry cannot create new identifiers. Pending entries for different matches remain independent, and new gameplay is always available.

## Status codes and errors (proposed)

| Status / transport outcome | Meaning | Client behavior |
| --- | --- | --- |
| 200 | Successful GET or existing PUT record | Render data or mark submission confirmed |
| 201 | First PUT commit | Mark confirmed; update both tabs |
| 400 / validation-error | Invalid pagination, configuration, record, or identifier agreement | Show actionable error; do not automatically retry |
| 404 / not-found | Unknown route/resource; known player with no matches instead returns an empty list | Show error; do not automatically retry |
| 429 / rate-limited | Temporary rejection | Bounded retry; preserve pending record |
| 500 / internal-error | Simulated server failure | Bounded retry; retain cached or pending data |
| 503 / unavailable | Simulated service unavailability | Bounded retry; allow manual recovery |
| Timeout / timeout | No response within proposed 5000 ms Axios timeout | Preserve outbox because commit status may be unknown |
| Connection failure / connection-failure | No HTTP response | Preserve pending data; gameplay stays usable |

HTTP failures return ApiError bodies. The client normalizes transport failures into the same error shape without pretending they have an HTTP status. Cancellation caused by navigation or supersession is not shown as a network error. See [Network scenarios](network-scenarios.md) for reproducible failures.

## TanStack Query strategy (proposed)

| Concern | Policy |
| --- | --- |
| Ranking query key | ['ranking', configKey, page, pageSize] |
| History query key | ['match-history', playerId, page, pageSize] |
| Submission mutation key | ['submit-match', matchId]; an outbox coordinator separately enforces one in-flight request per matchId |
| staleTime | 30000 ms for both queries; returning to a tab explicitly refetches even if still fresh |
| Query and mutation retries | At most 2 retries after the initial attempt for connection failure, timeout, 429, and 5xx; no automatic retry for other 4xx |
| Retry delay | Proposed deterministic 1000 ms then 2000 ms; no random jitter in tests |
| Post-registration | Invalidate all ranking and match-history query keys; refetch active views; keep inactive views invalidated until shown |
| Tab visibility | Refetch when a tab is displayed again; maintain independent page state and visible loading/empty/error/refresh states |
| Pending recovery | Read outbox on boot after MSW readiness, submit through the same mutation path, and keep manual retry after bounded retries fail |

Pass query cancellation signals through Axios. Cancel superseded requests when changing tabs, pages, configuration groups, or scenario; cancel affected reads before post-registration invalidation/refetch. A response belongs only to its full query key and current request generation. Ignore obsolete completions even if transport cancellation cannot stop them; never write late data into the currently selected view or overwrite a newer cache generation.

Proposed: scenario changes clear only ranking/history query caches after cancellation, then refetch; scenario state is not added to the production resource identity. Preserve existing cached data during ordinary background refresh and display an error without treating stale data as newly confirmed. The outbox owns persistence; the query cache is not the durable submission queue.

## Local persistence (proposed)

Increment 6 implements Options, immutable completed records, last-result and pending-outbox persistence. The last-result envelope is `{ version: 1, record: MatchRecord, submissionStatus }`; the outbox is `{ version: 1, entries: Record<string, { record: MatchRecord, attempts: number, lastError?: string }> }`. New entries are pending with attempts = 0. Writes order outbox before last result, allowing boot recovery of a newer queued result if the second write is interrupted. Invalid/unreadable outbox data is preserved and blocks overwrite. HTTP replay, confirmation, error status transitions and the MSW database remain pending; Retry Save retries local persistence only.

Increment 7 implements the three endpoints through real Axios/TanStack Query/MSW, including sending/error/confirmed state, boot/manual replay, shared confirmed records, grouping/sorting and pagination. Each HTTP attempt persists its counter first. Confirmation saves a matching last result before removing that queue entry, and acknowledged IDs are excluded from later storage merges. Interrupted acknowledgement can safely replay against first-write-wins PUT. Database writes must succeed before confirmation; failed persistence returns HTTP 500. Demo reset uses empty versioned result/outbox envelopes and reseeds only owned confirmed records.

Each value is a versioned, validated JSON envelope. Read only owned keys; invalid values fall back to defaults or an explicit recovery state. Do not clear unrelated localStorage data.

| localStorage key | Value and lifetime |
| --- | --- |
| pirate-battle.options.v1 | version, playerId, playerName, sessionTime, enemySpawnInterval; survives refresh |
| pirate-battle.last-result.v1 | version, completed MatchRecord, submission status, optional last error; abandonment does not overwrite it |
| pirate-battle.outbox.v1 | version, entries keyed by matchId with frozen MatchRecord, attempt count, and optional last error; delete entries only after confirmation |
| pirate-battle.msw-db.v1 | version, confirmed records keyed by matchId, fixture player identities, and database revision; both tabs read the same collection |

Proposed player identity: create a local UUID and display name Player on first visit and retain them in the options envelope; no authentication or name-entry flow is required by the challenge. Fixture players have stable distinct identifiers.

On boot, restore options/identity, last result, mock database, and outbox before data requests. Outbox entries take precedence over a stale last-result submission status; a confirmed replay updates the last result only if its matchId matches. A transient sending status restores as pending after refresh.

If storage writes fail, show persistence failure, retain the in-memory pending payload, and permit retry and gameplay; do not claim refresh recovery is guaranteed. Confirmed records and outbox entries survive refresh until the explicit demo reset defined in [Network scenarios](network-scenarios.md#restore-initial-state-proposed).

## Open questions

The challenge does not define payload field names, pagination limits, identity provisioning, configuration equivalence, or tie-breaking. These proposed contracts settle those choices for review; storage migration, simultaneous browser-tab writes, and changes to the ruleset still need implementation decisions.
